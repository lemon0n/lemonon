第一部分 设计原理：为什么是这个结构

1. 问题定义与三条公理

1.1 这个系统在解决什么问题

个人用 ETF 做中线波段，每天要回答四个问题：

  1. 今天市场处于什么状态，总仓位该给多少？
  2. 手里的几只，各自该留多少、减多少？
  3. 具体怎么下单：方向、份数、挂单价、费用？
  4. 什么情况下我判断错了、要改？

难点不在「算指标」，而在四个答案必须互相一致： 如果环境说「下行、上限 35%」，明细表却因为技术面强而建议加仓，用户就不知道该信谁。

1.2 旧版的病：四套判断同时在跑

位置 它当时在说什么 冲突点
规则卡 methodology 这只触发减仓 不知道用户有没有执行
目标仓位表 plan_v3 这只该占 8.9% 与规则动作不保证一致
执行后估算 执行完还剩多少仓 自己算一遍，与表里份数对不上
持仓分析（技术） 日线转强、缠论买点 与上面的减仓正好相反

修复不是「把文案写得更客气」，而是从结构上只保留一个出口。

1.3 三条公理

公理 含义 代码体现
A1 可复核 任一结论的数字都能在同一页找到同一口径来源 点评每句带数字；refs 指字段路径；明细表与个股卡同读 RS_PLAN
A2 可降级 缺数据时明说缺，不估算、不硬凑 ABSTAIN ≠ 持有；缺价/缺成本/缺昨收各自「—」；样本 <30 写「样本不足」
A3 单一出口 动作只由「目标仓位表 → 差额」派生 planActionOf() 只有一个实现；规则卡只做闸门与最早时点

这三条决定了后面所有顺序。

2. 为什么顺序是「数据 → 环境 → 结构 → 组合 → 执行 → 解释」

2.1 因果依赖图

规则卡（配置，先校验）
   │
   ▼
① 数据闸门 ── 不通过 ──▶ 只给事实，不给动作（终止决策链）
   │
   ▼
② 环境层：基准日线 → 市场状态 → 总仓位上限
   │            （没有它，后面不知道「总共允许多少」）
   ▼
③ 结构层：个股月/周/日 → 评分 → 单只上限
   │            （没有它，不知道「这只最多给多少」）
   ▼
④ 组合层：总额度 × 评分系数 × 波动 → 归一 → 单只目标权重
   │            （前三层的额度在这里合成）
   ▼
⑤ 执行层：目标 − 现仓 = 差额 → 确认条件 → 动作 → 挂单/份数/费用
   │            （没有目标就没有差额，没有差额就没有订单）
   ▼
⑥ 解释层：点评 / 个股卡 / 洞察
                （只能引用 ①–⑤ 的结论，不能自创）

2.2 每一步「为什么不能倒」

顺序 如果倒过来会怎样
先环境、后个股 先有总上限，个股评分再高也不能突破；倒过来会先算出「想买多少」，再被环境砍，用户看到两套数
先质量、后指标 不先判数据是否可用，就会用陈旧/合成数据算出「漂亮」的指标并出单
先目标、后动作 动作若先由规则决定，目标就沦为装饰，回到「四套判断」
先动作、后订单 订单必须由目标份额派生；否则份数与目标对不上，执行后仓位不平
先结论、后解释 解释若先写，会反过来影响结论（LLM 常见问题），无法复核
先主数据、后派生 快照/情绪若先算，会污染基准趋势这类可由真实日线算出的结论

2.3 三层额度的「只能收紧」规则

L1 环境：总上限 = 85 / 65 / 35 / 25（波动抬升再降 10）
   ↓ 只能往下压
L2 板块：单板块上限 = S25 / A20 / B10 / C5 / D0
   ↓ 只能往下压
L3 个股：单只上限 = S25 / A20 / B10 / C5 / D3
   ↓ 取三者最小值
目标权重 = min(单只上限, 板块压缩后的份额, 总上限分摊)

任何一层都不能把上层给的额度放大。这条写死在 plan_v3.build() 与前端 rsPlanRows() 的板块压缩里。

3.4 为什么规则求值（decide）在计划（plan）之前

看起来「先有目标才好决定动作」，但代码里 decide 先跑。原因：

  • decide 只依赖单腿特征 + 数据状态，不依赖组合；
  • 它输出的是「这只现在是不是触发风险退出/减仓/加仓」的规则结论；
  • plan_v3 输出「这只应该占多少」，两者独立计算；
  • 页面最终动作只取 plan；规则结论用于：①数据闸门 ②packet.legs[].action 的公开记录 ③个股卡解释。

如果让 plan 依赖 decide，规则卡就会重新变成「第二套动作来源」，违背 A3。

3.5 为什么状态合并要用「最差」

merge_status 优先级 ERROR > ABSTAIN > DEMO > DEGRADED > OK。 组合里只要有一只腿数据不可用，整体就不能宣称 OK——否则用户会以为所有结论都可靠。

4. 页面为什么这样排

4.1 阅读顺序 ≠ 计算顺序

计算顺序是依赖驱动（数据→环境→结构→组合→执行）； 阅读顺序是决策驱动：先给结论，再给证据，最后给远景。

一、持仓概况   我有多少钱、今天动什么、多少份什么价   ← 一屏内可执行
二、持仓分析   市场什么环境、组合跟不跟得上、每只为什么  ← 需要深读
三、市场洞察   接下来可能怎么走、还能看什么方向        ← 做下周打算

顺序不可倒：先讲理由再给结论，用户会自己在心里先形成一个动作，然后与表格冲突。

4.2 p1（市场概况）的内部顺序

顺序 区块 为什么在这
1 快照日提示 最先告诉读者「哪些数据不是今天的」，避免误读
2 四卡（成交/情绪/仓位区间/依据） 一屏给出全局状态
3 指数与均线 状态的原始证据
4 状态与情绪条目 解释状态怎么来的
5 阶段 → 仓位 → 我的持仓 把公开状态与个人仓位接上（唯一联动点）
6 板块概况 + 热力图 从大盘下沉到行业
7 国家队（最新一期） 背景资金，只作参考
8 行业成交额与占比 热力图的表格版（可查数）
9 轮动与主线 + 涨跌分布 结构结论
10 宏观四块 更慢的变量，放后面
11 政策与消息 当日扰动，最后

理由：从「最快变化」到「最慢变量」，从「结论」到「背景」。 用户如果只看前四块，已经能做仓位判断。

4.3 p5 的内部顺序

一、概况
   ① 四个数字        先知道钱
   ② 今日点评        再看今天做什么、为什么
   ③ 明细表          最后给可直接抄的下单信息
二、分析
   1. 市场环境       约束层：能不能进攻
   2. 组合情况       结构层：方向对不对、额度怎么分
   3. 个股分析       执行层：这一只怎么下手
三、洞察
   定性 / 赔率 / 情绪 / 情景 / 复盘 / 候选

为什么点评在表之前：点评回答「今天该不该动」，表回答「怎么动」。 先动后说原因，会让用户跳过大意直接抄单。

为什么个股在最后：它依赖前两层给的额度与板块结论；放前面会诱导「先看个股再找理由」。

4.4 渲染顺序（运行时）

D = window.DASHBOARD
  → render()                先出 p1 + p5/p7 骨架
  → autoUnlock()            有会话口令则解密
  → 解锁 → applyHold → render()（重绘，带持仓）
  → page5() 末尾 setTimeout(rsInit, 0)
       ① rsRenderBrief（先用已有数据出一版点评）
       ② rsRenderSector / rsRenderMarket / rsRenderDetail（骨架 + 占位）
       ③ 并行 fetchBars + rsFetchWeekly（每只持仓）
       ④ 全部回来 → rsAfterBars()
            → rsRefreshPlanTable()（重算目标与订单）
            → 再渲染点评、组合、个股、概率、候选、复盘

为什么允许「先渲染一版、再刷新」：

  • 持仓解密是本地异步操作，日线是跨域 JSONP，都不能阻塞首屏；
  • 首屏必须能看，否则用户以为坏了；
  • 数据到达后统一重算，保证「表格、点评、个股卡」来自同一份 RS_PLAN。

风险与对策：如果只刷新一部分，会出现「表说减仓、点评说持有」。 所以 rsAfterBars() 里先 rsRefreshPlanTable()，再渲染所有引用它的块。

6. 取数层

6.1 统一入口与三种来源

每个取数函数都走同一模式：

def daily(code, live_=None):
    if code in _CACHE['daily']: return _CACHE['daily'][code].copy()
    if use_live:
        df = live.fetch_daily(code)          # 东财 → 腾讯 → 新浪
        if df is not None:
            df = validate_bars(df, code)     # 列齐 / 可解析 / ≥30 根
            df.to_csv(cache_path)            # 落缓存
            STATE['daily'][code] = 'live'
            return df
    STATE['daily'][code] = 'snapshot'        # 降级
    note_fallback('%s 日线降级离线合成快照' % code)
    return snapshot.daily(code)

来源只有两种语义：

标记 含义 上层必须做什么
live 真实行情 可用于研究性决策
snapshot 离线合成快照 标 DEMO，禁止交易动作

6.2 未收盘 K 线剔除

def _drop_unclosed_today(df):
    now = utcnow() + 8h
    if now.hour > 15 or (now.hour == 15 and now.minute >= 5):
        return df
    return df[df['date'] != today]   # 15:05 前丢弃当日

原因：盘中三源都会返回「今日」这根没走完的 K 线，量比会变成 0.13 这种失真值。 日频信号只用已收盘 K 线；实时价只用于展示与市值。

12.2 页面订单（orderTicket，前端）

输入：持仓行 r、目标权重 targetW、总资产 total、可选限制 opt
1. 目标/价格/总资产缺失 → 直接返回原因
2. side = 目标 > 现仓 ? buy : (目标 < 现仓 ? sell : null)
3. limit = 买 ceil(现价×1.0001 / 0.001)×0.001
           卖 floor(现价×0.9999 / 0.001)×0.001
4. shares = floor(total × targetW/100 / limit / 100) × 100
   买入时 shares 不低于现有份额
5. delta = shares − 现有
   |delta| < 100 → 「不足一手」
6. 买入：可买手数 = floor(现金/limit/100)×100
   不够 → 下调并标「受现金限制」/「现金不足」
7. 成交额 < 0.1 亿 → 「流动性不足」；停牌 → 「停牌」
8. fee = max(5, 成交额×0.5bp) + 成交额×1bp
9. first = 卖出 |delta|×50% 向下取整到 100 份

12.3 为什么挂单价要「朝更优方向取整」

  • 买：向上进位 → 限价不低于目标价，成交概率更高；
  • 卖：向下截断 → 限价不高于目标价，更容易成交；
  • 两边都取到 0.001（ETF 最小变动价位），避免因取整把保护价吃掉。

15. 前端计算细节

15.1 解锁与解密

// 口令 → PBKDF2-SHA256(210,000, 16B salt) → AES-GCM-256 密钥
crypto.subtle.importKey('raw', pass, 'PBKDF2', ...)
  .then(k => crypto.subtle.deriveKey({salt, iterations, hash:'SHA-256'}, ...))
// 解密 {v,kdf,iter,salt,iv,ct}
crypto.subtle.decrypt({name:'AES-GCM', iv}, key, ct)
  .then(buf => JSON.parse(new TextDecoder().decode(buf)))

边界：

  • 非 https/localhost → crypto.subtle 不可用，提示「当前环境不支持浏览器解密」；
  • 没有密文 → 显示「创建空持仓」入口；
  • 口令错误 → 「口令不对，或密文文件已损坏」，不泄露细节。

15.2 盈亏计算（calcPort）

每只：
  last = 实时价（缺则 null）
  mv   = last × shares
  pnl  = (last − cost) × shares
  day  = (last − prev) × shares
     若缺 prev 但有涨跌幅 chg：day = shares × (last − last/(1+chg/100))

组合：
  totalPos = Σ mv
  totalAsset = totalPos + cash        # 只有全部有价才成立
  pnlPct = Σpnl / Σ(cost×shares)
  dayPnlPct = Σday / Σ(prev×shares)

为什么不用总资产做分母：现金会稀释百分比，同一只股票在不同现金比例下看起来盈亏不同。

15.7 概率（rsForecast）

特征：20 日动量 + 20 日波动
样本：历史上所有 t（t ≥ 20 且 t+h < n）
距离：二维标准化欧氏距离
取近邻：k = max(10, round(√n × 4))
权重：高斯核 exp(−0.5 × (d/band)²)，band = 近邻距离中位数（≥0.35）
输出：上涨占比（加权）、加权中位涨幅、有效样本数（1/Σw²）

样本 <20 → 该周期返回 null；页面整列显示「样本不足」。 概率不参与评级与动作。

15.8 缠论（rsChanOf / rsChanText）

分型：左右各 2 根
笔  ：顶底交替，间隔 ≥4 根，幅度 ≥1.5%
中枢：最近 4 笔的 3 段重叠，ZG = min(各段高)，ZD = max(各段低)
底背驰：最后是下降笔，价格创新低而 DIF 抬高
顶背驰：最后是上升笔，价格创新高而 DIF 走低
三买：现价 > ZG

rsChanText() 把结构翻译成六行：

行 内容
中枢 ZG/ZD 或「尚未形成中枢」
现价位置 中枢上方（距 ZG +x%）/ 中枢内 / 中枢下方（距 ZD −x%）
最近一笔 向上/向下笔 起价 → 止价（±x%）
结构信号 底背驰 / 顶背驰 / 三买 / 无
与目标的关系 按「动作 × 信号 × 位置」三维查表（见下）
持仓上下文 评级·上限 · 现仓→目标 · 板块及占比 · 大盘状态

「与目标的关系」真值表：

动作 信号/位置 文案
减仓 底背驰或三买 结构有企稳迹象，但仍按 50/30/20 减，不必一根大阴线砍完
减仓 中枢下方 弱势区，减仓不用等反弹，按计划执行
减仓 其它 无反向买点，按目标执行
加仓 顶背驰 不追高，等回踩中枢上沿不破
加仓 中枢下方 只做试错仓，等站上 ZG
加仓 其它 不反对，按确认条件分批
持有/等待 底背驰 只是观察理由，差额不足仍不动
持有/等待 顶背驰 提示风险，但不加仓、不提前卖

冲突裁决：

  • 个股在中枢上方 + 大盘下行 → 以大盘定总上限，个股强势只减不追；
  • 顶背驰 + 目标要加 → 以目标为准，但等回踩；
  • 底背驰 + 目标要减 → 以目标为准，买点只用来细分减仓节奏。

缠论不改目标、不改订单；要接入必须先在 docs/缠论融合回测方案.md 的 A/B 中过门槛。

15.9 市场洞察（marketOutlook）

定性打分：

状态：上行 +2 / 下行 −2 / 震荡 0
MA5 vs MA20：上 +1 / 下 −1
上涨家数占比：>55% +1 / <45% −1 / 其它 0
情绪分：≥65 +1 / ≤35 −1
总分 ≥2 偏多；≤−2 偏空；否则震荡

情绪温度：

成交额分 = clamp(50 + 环比×1.5, 0, 100)
趋势分   = 50 ±15（上行/下行）

情景三行（价位全部来自真实数据）：

震荡修复 前低 ~ MA20 现价距 MA20 ±x%

19. 今日点评提示词

19.1 外部生成契约（skills/portfolio-brief/SKILL.md 全文）

---
name: portfolio-brief
description: 生成持仓分析页「今日点评」的数据文件 data/brief.json。一次运行产出一份，页面只读、不改写。日期不一致、结构不合法或含禁词的，页面会丢弃并回退到本机引擎。
---

# 今日点评

输入：web/analysis_packet.json、data/brief_inputs.json（当次运行的行情、板块、资金、国家队、持仓与目标仓位）。
输出：data/brief.json。

## 输出结构

{
  "data_date": "2026-11-19",
  "conclusion": "一句话基调",
  "blocks": [
    {"k": "今天是什么日子", "v": "……", "refs": ["market.breadth", "market.glob"]}
  ]
}

- data_date 必须等于当次页面数据日；不一致整份作废。
- blocks 至少 6 块，k 不重复，v 不得为空。
- refs 写数据字段路径，便于回查；没有可不写。

## 必须覆盖的七类信息

大盘位置、量能、空间与赔率、行业与主线、资金、宏观与隔夜、自身组合。
缺哪类就在正文写「缺」，不得用别类数据顶替。

## 推理顺序

今天什么日子 → 大盘阶段 → 主要矛盾 → 行业信号 → 资金背景 → 自身偏差 → 今天动什么 → 什么情况下改判。

## 硬性要求

- 每句结论必须带数字，且数字能在页面同一处找到；找不到就不写。
- 动作只能引用目标仓位表（差额→动作→订单），不得另给方向。
- 不设字数、段数、句式限制；像人说话，不像公告。
- 禁止词：注意风险、保持谨慎、密切关注、综合来看、整体合理、酌情处理、有望、可能上涨、保证、必涨、稳赚、胜率。
- 不预测点位，不给目标价；概率类判断必须带样本量。
- 结尾写「价格是执行价，不保证成交。」（页面检测到就不重复追加）

19.2 页面兜底生成（rsBriefSections）的五段逻辑

外部文件缺失时，引擎按下面五段现场拼，每段都是「判断 + 数字依据」：

段 输入 生成逻辑
今日基调 时段、定性、仓位 vs 上限 仓位 > 上限 → 「任务是把这个差额还回去，不是找新机会」；低于上限 ≥5pct → 「有空间但只在确认满足时小步补」；贴合 → 「只做结构调整」
大盘与量能 状态、收盘、MA5/MA20、成交额环比 收在 MA20 下方 + 环比 ≤−5% → 「缩量阴跌不是放量恐慌，不急着抄也不急着砍到底」；放量下跌 → 「更像出货，按纪律减」；放量 → 「要看能否延续」；否则 「方向未定，结构优先」
结构 主线、过热板块、最大暴露、最低评级 主线 + 过热 → 「即便在主线也不追」；无映射 → 「板块暂缺，按单只计划执行」；最大仓位 = 最低评级 → 「结构错配，优先减它」
今天动什么 RS_PLAN 中有 order.delta 的行 有单 → 「买/卖 N 份，挂 x，首批 y，按 50/30/20 分批」；无单 → 「差额不足 3pct 或目标/价格缺失；不动也是动作」
改判 环境阈值 转好：收复 MA20 且 MA5 上穿；恶化：连续两日破 MA30 卖出剩余差额

中期趋势（MA60 方向） 「逐仓数据仅含 MA5/10/20，无法判断 MA60 与中期趋势」
单只的行业/政策驱动 「无可验证逐仓关联，仅作组合级背景」
「新变化」 「无历史对照，只陈述当前观察」
真实账户收益 「只有成本口径浮动盈亏，不代表账户累计绩效」

21.3 分析框架（五节）

  1. 证据效力与判断边界：行情日 vs 基准日、实时 vs 快照、持仓是否完整定价、分类是否完整、基准是否可用； 区分「市场问题 / 组合问题 / 数据问题」，数据问题不得解读成市场信号。
  2. 市场结构：趋势层级（短期 MA5/MA20、中期收盘 vs MA20/MA60）、波动（20 vs 60 日，抬升与否以标注为准）、 参与面、情绪与外围、宏观政策；结论落到「风险偏好与仓位纪律」，至少指出一个推翻条件。
  3. 组合诊断：仓位与状态的关系、结构失衡根源、盈亏归因、风险集中、现金弹性、执行可行性； 区分「规则建议 / 可执行订单 / 执行后模拟」。
  4. 逐只诊断：结构位置、量价关系、相对表现、市场与行业关系、规则动作逻辑、核心矛盾、反证与观察点。
  5. 决策与观察：是否需要动作（风险 → 结构 → 新增）；不需要时属于哪种原因；下次验证什么。

21.4 动作四层与反证三层

层次 字段 含义
规则动作 legs[].action 规则层动作码
研究候选 candidate_state READY 只表示通过门禁
可执行订单 orders[] 实际发布的订单
执行后可行性 validation.ok 约束是否通过

反证：①已观察到的反向证据（可引用字段）②当前未发现反证（只能写「未提供」）③待验证的失效条件。

21.5 禁止事项（原文摘录）

  • 不修改或重新推导 action、目标权重/份额、订单、风险门禁、规则阈值；
  • 不输出未经校准的胜率、上涨概率、目标收益、保证成交价格；
  • 不把静态模拟写成已成交，不把「无法判断」写成「继续持有」；
  • 不引用已撤回的旧回测收益或胜率结论；
  • 不使用「主力吸筹、试盘、出货、诱多」等不可观测因果作为证据；
  • 不制造每日必须买卖的节奏；无动作、等待确认都是有效结论；
  • 不在数据不足时用行业印象、常识或经验补出结论。

① 结构闸门：JSON 结构 / 必填字段 / blocks ≥6
② 日期闸门：data_date == 页面数据日
③ 禁词闸门：12 个词任一命中 → 丢弃
